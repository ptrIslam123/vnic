# Архитектура аппаратной эмуляции NIC

Данный документ описывает архитектурный подход к программной эмуляции сетевой карты (NIC), максимально приближенной к поведению реального оборудования. Цель - создать библиотеку, которая воспроизводит работу NIC на уровне, достаточном для качественного тестирования и разработки сетевых приложений, при этом сохраняя высокую производительность, сопоставимую с аппаратными решениями.

---

## Ключевые принципы

### 1. Минимизация копирований данных

Одно из фундаментальных требований - **минимизировать количество копирований пакетов**. Каждое копирование — это дополнительная нагрузка на CPU, шину памяти и кэш. Дальше все операции производятся через указатели.

### 2. Разделение на дескрипторы и буферы

Пакет не хранится как единый объект. Вместо этого вводятся **две сущности**:

- **Дескриптор пакета (PacketDescriptor)** - метаданные пакета: ссылка на буфер, длина, временная метка, флаги оффлоадов, номер очереди. Имеет фиксированный размер.
- **Буфер пакета (PacketBuffer)** - область памяти, в которой хранится полезная нагрузка (payload). Имеет фиксированный размер.

**Зачем это нужно:**
- Фиксированные размеры буферов упрощают управление памятью.
- Пул буферов заранее выделяет память блоками фиксированного размера, что исключает фрагментацию.
- Дескрипторы и буферы живут в разных пулах и переиспользуются независимо.

### 3. Цепочки буферов для больших пакетов

Если сетевой пакет превышает размер одного буфера, выделяется несколько буферов, и они связываются в цепочку через поле `next`. Один дескриптор ссылается на первый буфер цепочки, а каждый следующий буфер указывает на следующий.

**Преимущества:**
- Нет копирования при разбиении на сегменты.
- Jumbo Frames и TSO обрабатываются естественным образом.
- Малые пакеты (64 байта) занимают ровно один буфер.

## Роль Link: физическая среда передачи

### Концепция

**Link** - это физическая среда (кабель, оптоволокно), которая передаёт **сигналы**, а не пакеты. В программной эмуляции Link — это **чистая труба для байтов**. Он не знает ни о пакетах, ни об IP, ни о TCP/UDP.

**Что делает Link:**
- Передаёт байты между двумя точками.
- Создаёт виртуальную пару интерфейсов (veth-пару) в ядре Linux.
- Слушает один конец пары через сокет.
- Предоставляет метод `receive()` для чтения сырых байтов.
- Предоставляет метод `put()` для записи сырых байтов.

**Принцип:** Link - это труба. NIC - это устройство. Всё, что связано с обработкой пакетов, это ответственность NIC.

### Виртуальная пара интерфейсов (veth)

Link создаёт veth-пару в ядре Linux:
- **vethIn** (внешний конец) - в него пишут извне. Это «кабель», по которому данные приходят в NIC.
- **vethOut** (внутренний конец) - его слушает Link через сокет.

Когда внешний процесс пишет в `vethIn`, данные появляются на `vethOut`, откуда их читает Link. Это точная эмуляция физического кабеля: данные, отправленные на одном конце, появляются на другом.

### Метод receive()

`Link::receive()` - читает сырые байты из сокета `vethOut`. Это **блокирующий** вызов с таймаутом. Если данных нет, возвращает 0. Если данные есть - возвращает массив байт этого сетевого пакета.

### Метод put()

`Link::put(bytes)` - записывает сырые байты в сокет `vethIn`. Это используется для эмуляции передачи данных извне или для прямой подачи пакетов в Link (например, в тестах).

## Роль NIC: устройство обработки

**NIC (Network Interface Card)** - это устройство, которое:
- Получает сырые байты из Link.
- Преобразует их в пакеты (дескрипторы + буферы).
- Вычисляет RSS-хэш.
- Определяет номер очереди через RETA.
- Определяет NUMA-узел очереди.
- Выделяет буферы на нужном NUMA-узле.
- Применяет искусственную задержку (эмуляция пропускной способности).
- Помещает дескриптор в очередь.

 NIC сам опрашивает Link через метод `poll()`. Link не имеет фонового потока. NIC решает, когда забрать данные из Link.

**Почему это правильно:**
- В реальном NIC именно устройство управляет приёмом (через прерывания или polling).
- Link - пассивная среда, он не должен активно пушить данные.
- NIC контролирует темп обработки, что позволяет реализовать backpressure.

### Метод poll()

`NIC::poll()` - циклический метод, который вызывается из основного цикла обработки.

**Что делает poll():**
1. Вызывает `link_.receive()` для получения сырых байтов.
2. Если байтов нет - возвращает 0, цикл продолжается.
3. Если байты есть - вычисляет RSS-хэш.
4. Определяет номер очереди через RETA.
5. Определяет NUMA-узел этой очереди.
6. Выделяет буфер из пула нужного NUMA-узла.
7. Копирует данные в буфер — **единственное копирование**.
8. Применяет искусственную задержку, с учетом времени на копирование (эмуляция пропускной способности).
9. Помещает дескриптор в очередь.

## RSS и распределение по очередям

**RSS (Receive Side Scaling)** - технология, которая распределяет входящий трафик по нескольким очередям на основе хэша от полей пакета (IP-адреса, порты, протокол). Каждая очередь обслуживается своим ядром CPU, что позволяет параллельно обрабатывать трафик.

### Как RSS определяет NUMA-узел

1. RSS вычисляет хэш от 5-tuple (src IP, dst IP, src port, dst port, protocol).
2. Хэш используется как индекс в таблице RETA.
3. RETA возвращает номер очереди.
4. Каждая очередь привязана к определённому NUMA-узлу (через конфигурацию).
5. Буфер выделяется из пула этого NUMA-узла.

**Почему это важно:**
- Если буфер выделен на «неправильном» NUMA-узле, доступ к нему будет через межсокетную шину (QPI/UPI) — это медленее.
- Если буфер на локальном NUMA-узле - доступ быстрый.
- Для сетевых приложений это критично.

## Управление памятью

### Пул буферов

**MemoryPool** - это пул заранее выделенных буферов фиксированного размера. Все буферы выделяются один раз при инициализации, а затем переиспользуются.

**Зачем пул:**
- Исключает аллокацию памяти в горячем пути.
- Исключает фрагментацию памяти.
- Позволяет быстро выделять и освобождать буферы.

### NUMA-aware пулы

В системах с несколькими NUMA-узлами память делится на узлы. Каждый CPU-сокет имеет свой локальный узел памяти.

**Проблема:** если буфер выделен на «чужом» NUMA-узле, доступ к нему медленный.

**Решение:** пул на каждый NUMA-узел. Буфер выделяется из пула того NUMA-узла, который соответствует очереди, в которую попадёт пакет.

**Как это работает:**
- RSS определяет очередь.
- Очередь привязана к NUMA-узлу.
- Буфер выделяется из пула этого NUMA-узла.
- Дескриптор помещается в очередь.

**Результат:** все данные локальны для ядра, которое обрабатывает очередь.

**Цикл жизни буфера:**
1. Буфер выделяется из пула NUMA-узла очереди.
2. Данные копируются в буфер.
3. Дескриптор помещается в очередь.
4. Приложение забирает дескриптор.
5. Приложение обрабатывает данные.
6. Приложение возвращает дескриптор.
7. Буфер возвращается в свой пул.
8. Буфер снова доступен для выделения.

## Эмуляция пропускной способности

### Искусственная задержка

Реальный NIC имеет ограниченную пропускную способность (1 Гбит/с, 10 Гбит/с, 40 Гбит/с и т.д.). Это означает, что пакеты не могут передаваться быстрее определённой скорости.

**Как эмулировать:**
- Отслеживать время последней передачи.
- Вычислять, сколько байт можно передать за прошедшее время.
- Если пакет больше - подождать.

### Зачем это нужно

- Эмуляция реального поведения NIC.
- Тестирование приложений в условиях ограниченной пропускной способности.
- Предотвращение переполнения очередей при слишком быстрой подаче.

## Полный жизненный цикл пакета

### Приём (Rx)

1. **Link::receive()** — читает сырые байты из veth-сокета.
2. **NIC::poll()** — получает байты.
3. **RSS** — вычисляет хэш от 5-tuple.
4. **RETA** — определяет номер очереди.
5. **NUMA** — определяет узел очереди.
6. **BufferPool::allocate()** — выделяет буфер на нужном NUMA.
7. **memcpy** — копирует данные в буфер (единственное копирование).
8. **Задержка** — эмуляция пропускной способности.
9. **RxQueue::push()** — помещает дескриптор в очередь.
10. **Приложение::rxBurst()** — забирает дескрипторы из очереди.
11. **Приложение** — обрабатывает данные.
12. **Приложение::freeRxBurst()** — возвращает дескрипторы.
13. **BufferPool::deallocate()** — возвращает буфер в пул.

### Производительность

- **Одно копирование** — как при DMA.
- **Zero-copy** после первого копирования.
- **NUMA-local** — нет cross-NUMA доступа.
- **Пул буферов** — нет аллокаций в горячем пути.
- **Batch-обработка** — меньше накладных расходов.

### Гибкость

- **Link** — чистая труба, легко заменить (veth, tap, loopback).
- **NIC** — управляет всей логикой, легко расширять.
- **Пул** — общий ресурс, легко масштабировать.
- **RSS-контекст** — конфигурируемый.

---

Предложенная архитектура обеспечивает:

1. **Реализм** — поведение максимально близко к реальному NIC.
2. **Производительность** — одно копирование, zero-copy pipeline, NUMA-local.
3. **Гибкость** — легко расширять и модифицировать.
4. **Тестируемость** — каждый компонент тестируется независимо.
5. **Соответствие DPDK** — использует те же принципы (mempool, mbuf, RSS, RETA).
